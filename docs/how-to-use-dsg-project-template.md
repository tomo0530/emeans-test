# dsg-project-template を使った DS 検証案件の進め方

この文書は、`dsg-project-template` から作成した検証リポジトリを、案件開始から
Engineering チームへの引き渡し、案件終了まで一貫して使うための簡易ガイドです。
環境構築や各コマンドの詳細は [`README.md`](../README.md) を参照してください。

## 基本方針

検証リポジトリは、Notebook や一時的なスクリプトを置くだけの場所ではありません。
第三者が後から次の問いに答えられる状態を保つための記録です。

- 何の課題を、どの成功条件で検証したか
- どのデータ、コード、設定から、その結果が得られたか
- 結果をプロダクトへ組み込む際に、何を実装・運用すればよいか

探索や仮説検証は `experimentation/`、再利用するロジックは `project_module/` に置きます。
プロジェクト固有ではなく、複数案件で再利用できるファーストパーティライブラリは
`libs/` への配置を検討してください。

```text
探索・仮説検証              再利用可能な実装              プロダクト実装
experimentation/  -->        project_module/  -->          ENG 側リポジトリ
        |                         |
        +-- 結果・設定・根拠 -----+-- テスト・再現手順
```

Notebook から本番候補のコードを参照することはありますが、本番候補のコードから
Notebook を参照しない構成にしてください。

## 1. 案件開始時にやること

### 1.1 案件用リポジトリを作る

`abeja-inc/dsg-project-template` を直接クローンして案件作業に使うのではなく、
GitHub の **Use this template** から案件用の新規リポジトリを作成します。

作業を始めるホストには、少なくとも次を用意します。

- `docker compose`
- `git`
- `make`

GitHub との SSH 認証を済ませておくことも推奨します。GitHub CLI や Gitleaks を
ホストで使う場合は、必要に応じて追加で導入してください。

```bash
docker compose version
git --version
make --version
```

### 1.2 README を案件向けに更新する

`README.md` は、案件リポジトリの基本情報を集約する文書です。案件開始時には、
テンプレート内のコメントを参考に、その時点で決まっていること・分かっていることを
案件固有の内容へ置き換えます。未確定事項を推測で埋める必要はありません。

開始時には、少なくとも次の項目を確認・記入します。

- 概要: 案件の目的、想定する成果、案件ページへのリンク
- 利用した技術・手法、アーキテクチャ: 採用済みのものがある場合
- Setup Instructions: 必要なツール、環境構築、環境変数、外部サービスの設定
- Datasets Description: データを扱う場合の入手元、識別情報、配置先、アクセス権、匿名化
- 制約事項・既知の課題: 開始時点で把握している前提や利用上の注意

実行方法、再現用シナリオ、テストと静的解析、最終成果や未解決事項は、
案件の進行に合わせて追記し、終了時に完成させます。

### 1.3 検証環境を準備する

通常の作業は Docker 開発コンテナ内で行います。CPU / GPU の選択、
`.env.container` の `WITH_*` 設定、起動方法の詳細は `README.md` を参照してください。

```bash
make docker-up-cpu       # GPU を使う場合は make docker-up-gpu
make docker-shell        # VSCode のコンテナアタッチでも可
```

コンテナの初回起動時には、Git hook の自動設定と `uv sync --all-groups` が実行されます。
コンテナを使わずホストで作業する場合や、このリポジトリで `.githooks` に切り替えたい場合は、
必要に応じて次を実行してください。

```bash
make setup-hooks
```

`.env.container`、ソースコード、Notebook、ログには、API キー、トークン、
パスワード、PII を書かないでください。

## 2. 案件中の使い方

### 2.1 探索は experimentation に置く

最初は `experimentation/notebooks/` で仮説を素早く検証して構いません。
Notebook だけでなく、一時的な `.py` ファイルを担当者用ディレクトリに置いて実験しても問題ありません。

```bash
mkdir -p experimentation/notebooks/<your-name>
cp experimentation/notebooks/templates/base_template.ipynb \
  experimentation/notebooks/<your-name>/quick_validation.ipynb
```

Notebook テンプレートには、目的、主要な結果、結果から言えること、実行日時、
Python / OS 情報、乱数 seed、データ版を記録する欄と、Push 前の機密情報確認項目があります。
`README.md` の案件情報を補完する実験記録として使い、Notebook は上から順に実行できる状態を保ちます。

### 2.2 再利用するロジックは project_module に移す

採用候補になった前処理、特徴量生成、評価、推論ロジックは
`project_module/src/project_module/` へ移し、`project_module/tests/` にテストを追加します。

```bash
make fix project_module
make all-lint project_module
make test project_module/tests
```

探索結果には、少なくとも以下を紐付けます。

- データのバージョンまたはスナップショット ID
- コードのコミット SHA とブランチ
- 実行設定、乱数 seed、ハイパーパラメータ
- 実行日時、実行者、モデル成果物の保存先またはハッシュ
- 主指標、比較対象、失敗ケース、採否判断

乱数 seed と環境を固定し、数値比較では浮動小数点の誤差を考慮します。
データそのものや生成物をコミットする前には、ライセンス、権限、容量、PII の有無を確認してください。

### 2.3 継続的に品質を確認する

変更ごとに、対象に応じて次の確認を行います。実行は原則としてコンテナ内です。

```bash
make fix <path>
make all-lint <path>
make test [<test_path>]
make secret-scan [<path>]
```

コミット前には Notebook の出力を消去してください。

```bash
make reset-notebook experimentation/notebooks
```

CI が通っていても、評価指標、出力スケール、欠損、全 NULL 列など、
検証結果そのものが妥当かを確認します。

### 2.4 意思決定を残す

再現性だけでなく、なぜその方式を選んだかも残します。例えば、
「候補 B は精度が高いが推論時間が上限を超えたため不採用」
「特定セグメントで性能低下があるため追加データが必要」といった判断を、
結果と同じ場所に記録します。

結論が「実装しない」場合も、有効な案件成果です。

## 3. ENG へ引き渡す

ENG への引き渡しは、Notebook とスコア表の共有だけで完了ではありません。
ENG が必要に応じて検証を再現し、実装・運用の見積もりをできる状態を完了条件にします。

最低限、次を引き渡します。

| 区分 | 引き渡すもの |
| --- | --- |
| 目的と判断 | 解く課題、利用者、成功条件、採用案、未解決の制約 |
| 入出力契約 | 入力項目、型、単位、必須性、出力形式、エラー時の挙動 |
| 実装 | `project_module/` の再利用可能なロジック、依存関係、実行コマンド |
| 再現 | データの参照方法・版、設定、seed、コミット SHA、期待する評価値 |
| 品質 | `make all-lint`、`make test`、`make secret-scan` の結果または通過状況 |
| 運用 | 推論頻度、レイテンシ、コスト目安、監視指標、再学習・ロールバック方針 |
| リスク | データリーク、バイアス、性能劣化、PII・権限、既知の失敗ケース |

データを ENG に直接渡せない場合は、データの所在、取得手順、必要な権限、
スキーマ、サンプルまたは合成データ、検証用スナップショットの識別子を連携します。
認証情報や個人情報を成果物に含めないでください。

本番に必要な API、インフラ、認可、監視の実装は原則として ENG の責務です。
DS は、特徴量、モデル、評価、データ要件を明文化し、実装差分が評価結果を壊さないことを確認します。

## 4. 案件終了時にやること

終了時点の検証を、将来たどれる状態に固定します。

- 採用・不採用と根拠、達成した指標、比較対象を README または最終レポートへ記録する
- 最終実験のコード SHA、データ版、設定、seed、モデル成果物の参照先を記録する
- 再現用シナリオを README に記載し、第三者が実行できることを確認する
- Notebook の出力を除去し、機密情報、PII、不要なデータを含めないことを確認する
- `make all-lint`、`make test`、`make secret-scan` を実行し、結果を残す

モデルやデータ成果物を保管する場合は、リポジトリに無理にバイナリを追加せず、
承認済みの保管先と識別子を記録します。保持期間、閲覧権限、削除・失効の方法も
案件のルールに従います。

終了前に、`README.md` の必須項目と案件に該当する項目を案件固有の内容で埋め、
テンプレート用のコメントを削除します。必要情報が `README.md` 以外の文書にある場合は、
`docs/` 配下などに置き、README から参照できるようにしてください。

## 終了チェックリスト

- [ ] 目的、成功条件、最終判断、担当者を記録した
- [ ] 最終結果をデータ版、コード SHA、設定、seed まで遡れる
- [ ] ENG が必要な実装、データ、運用情報を受領し、責務境界を合意した
- [ ] 再現シナリオを第三者が実行できた
- [ ] `make all-lint`、`make test`、`make secret-scan` が完了した
- [ ] Notebook 出力、データ、ログ、ドキュメントに Secrets・PII がない
- [ ] README の必須項目と案件に該当する項目を案件固有の内容で埋めた
- [ ] README のテンプレート用コメントを削除した
- [ ] README_en.md を維持する場合、README.md と整合するよう更新した
- [ ] 制約事項、既知の課題、未解決事項、利用上の前提を記録した
- [ ] ライセンス、担当者・連絡先、関連リンクを最終状態に更新した
